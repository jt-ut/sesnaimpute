# W63 — one completeness limit per band, read alike; a coupled band's recovery is diagnostic, not substituted; retention floored below the 50% point

Branch `catalog-w63`, worktree `../sesnaimpute-w63`. Part A unchanged
throughout. Part B corrected twice by the coordinator: first, the flag
moved from fit-vs-histogram to the recovery curve evaluated at the fitted
`F_50`; second (this round), the limit substitution was reverted —
`LIMIT_KIND` and the recovery fraction stay report-only, `F_50_REGION_MJY`
is always the counts fit. A third change, this round: `population/
field_stars.py`'s retention floor is lowered by three roll-off widths
below the region's deepest limit.

## Part A — one limit, three readers (unchanged)

`depth_grid._region_band_counts_fit`'s counts-based `F_50_REGION_MJY`/
`W_REGION_DEX` is the only Spitzer fit, written as the per-source product
`catalog/sesna/limits_sesna_source__<R>.hdf5`; `catalog.limits.limits`
reads only that file (confirmed by grep, `fittp/likelihood.py:303`
unchanged). `depth_grid`'s `F_LIM_50_PIX_MJY`/`F_LIM_50_MED_MJY` collapse
into the pixel median of the same per-source array.

## Part B — reverted: recovery curve is REPORT-ONLY, no substitution

The coordinator's reason, now in the module docstring: for a pair the
two-band rule makes mutually required at the faint end (3.6/4.5 µm for
field stars), a catalogued source carries both by construction, so the
measured fraction of EITHER band among catalogued sources is near 1
whatever its true recovery — the estimator is a tautology for that pair
and cannot bound either band's recovery. The pair's inclusion is measured
only jointly, and each band's counts fit is that joint inclusion
projected onto the band. `_recovery_crossing` and `MIN_RECOVERY_BIN_SOURCES`
(the substitution machinery from last round, including the bug fix for
its bright-end noise) were removed as now-dead code; `_truncation_test`
still returns `(truncated, recovery_at_f50, limiting_band)` for the
report, but `build()` no longer touches `f50_region_mjy` — `F_50_REGION_MJY`
is bit-identical to the Part-A-only run for every band in every region.
`LIMIT_KIND` is still written to the per-source product (report-only).

## Retention: floored three roll-off widths below the deepest limit

`population/field_stars.py`'s `deepest_limits` now multiplies the
region's 1st-percentile per-source limit (per band) by `10**(-3 *
W_DEX[b])`, `W_DEX` read from `catalog.depth_grid`'s per-source limits
product (`ROLL_OFF_WIDTHS = 3.0`, new constant, cited to the coordinator's
2026-09-10 ruling in the module docstring: the completeness model's own
acceptance is under 1% three widths below the 50% point, so nothing the
real catalogue could plausibly hold is cut by this floor).

Reran `population.field_stars` for Perseus and NGC 7129 (`n_jobs=14`,
`capped.sh`, `CAPPED_CEILING_KB=8388608`, foreground). Retained-star
counts, before (pre-existing products, backed up to
`scratchpad/w63/field-stars_trilegal_region__<R>.hdf5.bak`) vs after:

| region | n_raw | n_retained before | n_retained after | wall time (after) | peak resident |
|---|---|---|---|---|---|
| Perseus | 3,663,957 | 1,270,711 | **2,158,933** | 18.6 s | 1951 MB |
| NGC 7129 | 69,936 | 14,113 | **40,076** | 0.4 s | 1951 MB (shared process) |

Perseus retains 1.70× as many stars, NGC 7129 2.84× — both regions' deep
floors moved substantially fainter (e.g. Perseus I1's `W_DEX=0.159` dex
gives `10**(-3×0.159)` ≈ 0.33×, a factor of ~3 fainter, applied to the
1st-percentile limit in every band; NGC 7129's own per-band `W_DEX` is
wider for some bands, giving a bigger drop still), consistent with the
coordinator's point that the catalogue holds sources well below the
fitted 50% point that the un-floored retention was cutting.

## Disclosed side effect, not fixed here (out of this round's scope)

`population/star/population_star_tile__<R>.hdf5`'s `STAR_INDEX` column
indexes rows of `population/trilegal/field-stars_trilegal_region__<R>.hdf5`.
Rebuilding field-stars with a different retention floor changes which
rows survive and in what order, so `STAR_INDEX` in the (unrebuilt)
star-population-tile product for Perseus and NGC 7129 is now stale until
that stage is rebuilt too — confirmed by a spot check (rerunning the
Perseus STAR per-bin atlas diagnostic against the new field-stars file
with the old star-population-tile file gives numbers inconsistent with
both the pre- and post-field_stars states). Left for the coordinator: the
downstream rebuild order (`population.star` → `bmstp.atlas`) for any
region whose `population.field_stars` changes.
